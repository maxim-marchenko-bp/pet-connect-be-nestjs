## Findings

### F1 — [stage-1] AC-05 "maximum page size" not enforced — **Fix now**

- **Where:** `src/shared/types/generic-filter.ts:8` (`pageSize` has only `@Transform(Number)`; no `@Max`/`@Min`/`@IsInt`) + `src/common/list-filter/services/list-filter.service.ts:31` (`take: filters.pageSize`, unclamped).
- **Touches:** AC-05; contract `openapi.yaml:84` (`pageSize maximum: 100`); NFR §6 read-p95 (assumes bounded pages).
- **Failure:** `GET /api/pets/list?pageSize=100000` returns up to 100000 rows — the "bounded pages with a maximum page size" clause of AC-05 is unmet, and no test asserts the bound (`test/pet-view.e2e-spec.ts:50` only exercises `pageSize=2`). Confirmed by the review owner.
- **Resolution:** Fix now. Add `@Type(() => Number) @IsInt() @Min(1) @Max(100)` to `GenericFilter.pageSize` (and `@Min(1)` to `page`) and add a list test asserting an over-max request is clamped/rejected. Note: `GenericFilter` is shared (also used by the `user` module) — verify no regression there.

### F2 — [stage-2] add-co-owner never validates target-user existence; `UserService` is a dead dependency — **Remove dead injection**

- **Where:** `src/modules/pet/pet.service.ts:30` (`userService` injected) and `:131-145` (`addCoOwner` never calls it).
- **Touches:** AC-09b; `sad.md §6` flow 9; `openapi.yaml:201-205` (400 branch, OQ-1).
- **Failure:** adding a non-existent `userId` falls through to a `user_pets` FK violation mapped to a generic `400 "Invalid reference"` rather than an explicit "target user unknown". Behaviourally backstopped by the FK (not a security hole); the spec test-plan + openapi explicitly deferred the explicit check as open question OQ-1. The injected `UserService` is currently unused code.
- **Resolution:** Remove the unused `UserService` injection now; keep the explicit existence check deferred per OQ-1.

### F3 — [stage-2] Aggregate `npm run test:e2e` is red — **Fix now**

- **Where:** `test/jest-e2e.json:5` now runs every `*.e2e-spec.ts`, including the pre-existing broken `test/app.e2e-spec.ts` (expects `GET /` → 200 "Hello World!"; no `AppController` route exists → 404).
- **Touches:** CI hygiene (no AC).
- **Failure:** the feature's own e2e command exits non-zero, so a future pet e2e regression can hide behind the already-failing suite.
- **Resolution:** Fix now. Delete the stale `test/app.e2e-spec.ts` scaffold test so the green/red signal is trustworthy.

### F4 — [stage-2] Response shape carries fields the contract forbids — **Relax openapi**

- **Where:** `src/modules/pet/mappers/to-public-pet.ts:5-6` strips only `users`, so `Pet` responses include `createdAt`/`updatedAt` and the full nested `type`, while `openapi.yaml:295-303` declares `Pet`/`PetType` with `additionalProperties: false`.
- **Touches:** AC-01/AC-04/AC-06b (contract conformance). No privacy impact (no credential fields).
- **Failure:** extra timestamp/nested-type fields vs the documented schema. Consistent with the repo convention (`to-public-user.ts` likewise keeps timestamps) — an openapi over-specification, not a regression.
- **Resolution:** Relax the openapi `Pet`/`PetType` schemas to match the established serialization convention (allow timestamps + nested type).
